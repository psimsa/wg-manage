# Spec 003 — Terminal UI (TUI)

## Problem

Today every change means editing `config.yaml` by hand: adding peers, picking
IPs, writing iptables NAT rules (including the correct egress interface),
and writing `peerOverrides` blocks. The goal: **no manual YAML editing**.

## Proposal

Add a `tui` command (`wg-manage tui`, short `t`) that opens an interactive
terminal UI over the loaded YAML file. Save happens on explicit action
(`Ctrl+S` / menu), so the user can experiment safely.

### Library

Use a mature, actively maintained TUI library rather than hand-rolling
terminal handling. Candidates (evaluate at implementation time):
**Bubble Tea** (`charmbracelet/bubbletea` + `bubbles` + `lipgloss`) —
idiomatic, well-documented, easy to test (the model is a pure
`Update(msg) (Model, Cmd)` function). This is the recommended default.
Alternative: `tview` (rivo) if richer widgets are needed.

### Layout

```
┌─ wg-manage ─────────────────────────────────────────────┐
│ [Peers] [Settings] [Network]                            │  ← tabs
│                                                         │
│ Peers tab:                                              │
│  > Server      10.0.2.1/32   endpoint=vpn.example.com  │  ← list, ↑↓ to move
│    My Laptop   10.0.2.2/32                              │
│    My Phone    10.0.2.3/32                              │
│                                                         │
│  a=add  e=edit  d=delete  r=toggle routing  o=overrides│
│  g=generate  s=save  q=quit                             │
└─────────────────────────────────────────────────────────┘
```

### Views

1. **Peers** — list of peers (name, first address, endpoint, server/client
   badge). Keys:
   - `a` — add peer: form with name, role (server/client), endpoint (servers
     only). IP is **auto-allocated** (spec 002); shown read-only in the form.
   - `e` — edit peer: form with all editable fields (name, description,
     address list, DNS, MTU, table, listen port, fwmark, keepalive,
     pre/post up/down, saveConfig).
   - `r` — routing helper (server peers): toggles NAT/forwarding PostUp /
     PostDown lines. The **egress interface is a field in the form**
     (default from `settings.serverDefaults.egressInterface`, e.g. `eth0`),
     replacing the hardcoded `eth0` in today's `bootstrap`. Generates the
     same sysctl/iptables lines as `add -add-routing` plus the MASQUERADE
     rule for the chosen interface, with `%i` available for wg-quick.
   - `o` — overrides editor: pick a target peer (by name, resolved to its
     public key), then edit the free-form extra lines list for that peer's
     `[Peer]` section in the current peer's config (`peerOverrides`).
   - `d` — delete peer (with confirm); address returns to the pool.
   - `g` — run `generate` with current settings (writes `output/`), show
     result summary.
2. **Settings** — form over the `settings` section (spec 001): ipPool,
   subnets (servers/clients CIDRs), serverDefaults (listenPort,
   egressInterface, keepalive, postUp/postDown), clientDefaults,
   generate (outputDir, png). Validates on save (CIDR syntax, subnet
   containment, pool size).
3. **Network** — the visualization from spec 004 embedded as a tab.

### Behavior

- All edits go through the same `models` + IPAM functions the CLI uses, so
  TUI and CLI can never diverge. No separate "TUI model".
- `s` / `Ctrl+S` writes YAML via `models.SaveYaml` (same formatting as
  `format`). `q` quits; if there are unsaved changes, ask to save/discard.
- The TUI never requires root; it only edits files.
- Config file selectable via `-config` flag, default `config.yaml`.

### Testing

Bubble Tea models are testable by feeding `Msg`s into `Update` and asserting
on the resulting model state — no terminal needed. Cover: add/edit/delete
peer flows, routing helper generating correct lines for a custom egress
interface, overrides editing, settings validation, save round-trip.

### Acceptance criteria

- [ ] `wg-manage tui -config config.yaml` opens the UI; all three tabs work.
- [ ] A new peer can be added without touching YAML; IP auto-assigned from
      the pool/subnet.
- [ ] Routing helper on a server peer inserts correct PostUp/PostDown with a
      user-specified egress interface.
- [ ] Overrides can be added for any peer without knowing public keys.
- [ ] Saving produces a YAML that `generate` (CLI) renders correctly.
- [ ] Works on existing configs without `settings` (creates defaults on
      first save).
- [ ] Unit tests for the model update logic.
